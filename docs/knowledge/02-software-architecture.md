# Synthstrom Deluge Community Firmware: Architecture Report for `src/deluge`

Repo: `<upstream>`, commit `2cd3091` (2026-10-08). All paths below are relative to `<repo>/src/` unless they are written out in full.

**The short version:** the firmware is about 238k lines. The GUI makes up 38% of it. The model, engine and GUI layers all call into each other through roughly 15 global singletons, so there is no clean layering. Removing a single feature is usually easy to hard. Removing a whole layer such as the GUI or playback would mean rewriting the core.

## 1. Boot and main loop: `deluge/deluge.cpp` (1,054 lines)

`deluge_main()` (line 643) runs in this order:
1. Detects OLED vs 7-segment from the bootloader's DMA config and sends startup commands to the PIC (pad/button microcontroller).
2. Calls `functionsInit()` and sets `currentPlaybackMode = &session`.
3. Sets up GPIO, CV SPI and the OLED. Creates `display = new OLED` or `new SevenSegment` (lines 703-718).
4. `ssiInit` (audio codec), then `encoders::init`, `cvEngine.init()`, `AudioEngine::init()`, `audioFileManager.init()`.
5. `initSPIBSC()`. The comment notes that audio and graphics routines are injected into the SPIBSC wait loops.
6. Factory-reset check via a PIC read callback.
7. `FlashStorage::readSettings()`, `runtimeFeatureSettings.init()`, USB host, then USB peripheral as fallback.
8. Reads the SD-card settings files: `runtimeFeatureSettings.readSettingsFromFile`, `MIDIDeviceManager::readDevicesFromFile`, `midiFollow.readDefaultsFromFile`.
9. `setupBlankSong()`, then queues `addConditionalTask(setupStartupSong, …, isCardReady)`.
10. `registerTasks()` and `startTaskManager()` (lines 915-917). `mainLoop()` (line 605) is the non-scheduler fallback and is not used.

**Registered tasks** (`registerTasks()`, line 531). Lower priority number = more important.

| Pri | Task |
|---|---|
| 0 | `AudioEngine::routine_task` (min 8, target 64, max 128 samples at 44.1k) |
| 1 | USB MIDI input poll |
| 2 | encoder interpretation |
| 3 | `playbackHandler.routine()` |
| 4 | `playbackHandler.midiRoutine()` |
| 5 | `audioFileManager.loadAnyEnqueuedClusters` |
| 6 | `AudioEngine::slowRoutine` |
| 7 | buttons/pads |
| 11 | `doAnyPendingUIRendering` |
| 12 | `smSysex::handleNextSysEx` |
| 21 | `audioFileManager.slowRoutine` |
| 22 | `audioRecorder.slowRoutine` |
| 23 | `playbackHandler.slowRoutine` |
| 31 | `PIC::flush` |
| 32 | `oledRoutine` |
| 33 | `uiTimerManager.routine` |

**Re-entrancy hooks** (C entry points called from drivers):
- `routineForSD()` (line 971) is the busy-wait called during long SD reads. It runs audio, then cycles through OLED / encoders / buttons.
- `yieldingRoutineForSD` / `yieldingRoutineWithTimeoutForSD` call the scheduler's `yield()`.
- `routineWithClusterLoading`, `loadAnyEnqueuedClustersRoutine`, `sdCardEjected`.
- `sdRoutineLock` and `intc_func_active` guard against recursion.

`deluge.cpp` also owns:
- `readButtonsAndPads()` (line 249), which reads PIC UART bytes and dispatches to `matrixDriver.padAction` and `Buttons::buttonAction`.
- `setUIForLoadedSong`, `setupBlankSong`, `setupStartupSong`, `deleteOldSongBeforeLoadingNew`.

So the boot file knows about song loading and the UI.

## 2. Task scheduler: `src/OSLikeStuff/` (1,553 lines)

- `scheduler_api.h` is the C API: `addRepeatingTask(handle, priority, backOff, target, max, name, resource)`, `addOnceTask`, `addConditionalTask`, `yield(RunCondition)`, `yieldWithTimeout`, `yieldToIdle`, `runTask`, `blockTask`/`unblockTask`, `getAverageRunTimeForTask`, `ignoreForStats`.
- Resource flags: `RESOURCE_SD`, `RESOURCE_USB`, `RESOURCE_SD_ROUTINE`.
- `task_scheduler/task_scheduler.cpp` (465 lines) is the cooperative, non-preemptive scheduler. `TaskManager::chooseBestTask(deadline)` (line 51) picks the highest-priority ready task whose running-average duration fits before a more important task's latest start time. It forces any task that has passed its `maxInterval`, and can fall back to lower-priority fillers.
- `kMaxTasks = 25` (`task_scheduler.h:18`).
- `yield()` runs other tasks while one task waits, which is how SD loading stays responsive.
- `timers_interrupts/` sets up the hardware timers. Timer 2 is `TIMER_MIDI_GATE_OUTPUT`, used to schedule sample-accurate MIDI clock and gate output between audio renders (`audio_engine.cpp:980-1030`).
- `fault_handler/` handles crash dumps.
- Unit-tested in `<repo>/tests/unit/scheduler_tests.cpp`.

**Coupling:** low and clean. The audio engine reads its own task stats (`getAverageRunTimeForTask(routine_task_id)`) to estimate CPU load, so the scheduler doubles as the CPU meter.

## 3. Audio engine: `processing/engines/audio_engine.{h,cpp}` (1,885 lines)

`namespace AudioEngine` is a namespace full of globals, not a class. Key state:
- `currentSong`-driven rendering
- `renderingMemory` / `reverbMemory` buffers (`SSI_TX_BUFFER_NUM_SAMPLES`, max 128)
- `cpuDireness`, `audioSampleTimer`, `renderInStereo`, `bypassCulling`
- the reverb object and `reverbSidechain`
- the sample-preview `SoundDrum` (`sampleForPreview`)
- the list of `SampleRecorder`s (`firstRecorder`)
- `deluge::fast_vector<Sound*> sounds`, a global registry of every Sound, used for culling

**Render path:**
1. `routine_task()` calls `routine()` (line 1046). `routine()` loops `doSomeOutputting()` and `routine_()` up to twice.
2. `routine_()` (line 563) is the hot path:
   - reads the SSI DMA TX position (`getTxBufferCurrentPlace()`) to find how many samples are free. Audio is **polled, not interrupt-driven**.
   - `flushMIDIGateBuffers()`
   - `setDireness(numSamples)`, which handles culling
   - doubles and rounds the window to a multiple of 4 for NEON
   - `tickSongFinalizeWindows()` (line 737), which shortens the window to land exactly on the next sequencer tick, calls `playbackHandler.actionTimerTick()` / `actionSwungTick()`, and schedules MIDI and trigger clock-out
   - `renderAudio()`
   - `scheduleMidiGateOutISR()`
3. `renderAudio()` (line 635) runs, in order:
   - `currentSong->renderAudio(buffer, reverbBuffer, sideChainHit)`
   - `renderReverb()`: global send reverb with sidechain ducking, auto-off after 12 s of silence
   - `renderSamplePreview()`: only when the current UI is the sample browser or slicer, so the engine checks `getCurrentUI()`
   - `renderSongFX()`: song-level filters, SRR/bitcrush, stutter, pan, master compressor (`currentSong->globalEffectable`)
   - `metronome.render`
   - RMS envelope follower
   - input monitoring setup
4. `doSomeOutputting()` (line 1132) copies to the I2S TX ring with master volume, dither and saturation. It mixes in input monitoring and feeds `SampleRecorder`s (output or input recording).
5. Offline stem export uses a separate branch in `routine()` (`renderAudioForStemExport`, line 670), which renders 32-sample blocks faster than real time.

**Voice allocation:**
- Pools: `VoicePool`, `VoiceSamplePool`, `TimeStretcherPool` are `deluge::memory::ObjectPool<…, fast_allocator>` (`audio_engine.h:139-141`, `memory/object_pool.h`).
- Per Sound: `Sound::acquireVoice()` (`processing/sound/sound.cpp:4901`) enforces `maxVoiceCount` (default 8) and otherwise steals with `stealOneActiveVoice()` / `getLowestPriorityVoice()` (lines 4943-4956).
- Rate limit: `allowedToStartVoice()` (`audio_engine.cpp:1428`) allows 4 new voices per render, or 1 when direness is above 12.

**CPU-load culling:**
- `setDireness()` (line 503) turns the scheduler's measured DSP time into `cpuDireness` (0-14). It rises immediately and decays with hysteresis.
- `cullVoices()` (line 427) acts on how far the render is over its limit:
  - 32 or more samples over (hard): kill half and terminate half, plus one force-release
  - mildly over (soft): `forceReleaseOneVoice`
- The kill functions (lines 277-379) search all voices globally through the `sounds` registry. If there are no voices, they fall back to `currentSong->cullAudioClipVoice()`.
- `cpuDireness` is also read inside DSP to lower quality: `dsp/oscillators/oscillator.cpp` (wavetable/band-limit table choice), `dsp/filter/lpladder.cpp:69`, `model/sample/sample_controls.cpp`.
- `TimeStretcher` sets `AudioEngine::bypassCulling` (`dsp/timestretch/time_stretcher.cpp:267`).

**Related:**
- `processing/engines/cv_engine.{h,cpp}` (~530 lines): CV and gate output over SPI DAC, plus gate timers.
- `processing/audio_output.cpp`: the audio track Output.
- `processing/metronome/`
- `processing/live/`: `LiveInputBuffer` and `LivePitchShifter`, for live audio input used as an oscillator.
- `processing/stem_export/stem_export.cpp` (1,194 lines).

## 5. Synth engines (Sound and Voice)

**Class layout:**
- `Sound : ModControllableAudio, virtual Voiced` (`processing/sound/sound.{h,cpp}`, 5.4k lines) is the patch-level object. It holds:
  - `Source sources[2]`, `Patcher patcher`, `globalLFO1/3`, `LFOConfig`
  - `synthMode` (SUBTRACTIVE / FM / RINGMOD)
  - polyphony mode, unison count/detune/spread, modulator transposes
  - the `voices_` vector of `ActiveVoice` (`unique_ptr` from the pool)
  - delay, compressor, arpeggiator settings, sidechain
- Concrete types: `SoundInstrument : Sound, MelodicInstrument` (synth track) and `SoundDrum : Sound, Drum` (kit row).
- `Voice` (`model/voice/voice.{h,cpp}`, 2.7k lines) holds:
  - its own `Patcher`
  - `unisonParts[kMaxNumVoicesUnison]` (each with `VoiceUnisonPartSource`, `voice_unison_part_source.cpp`)
  - 4 `envelopes` (`modulation/envelope.cpp`), local `lfo2`/`lfo4`
  - a `dsp::filter::FilterSet`
  - `paramFinalValues`, `sourceValues[kNumPatchSources]`
  - `guides[kNumSources]` (`VoiceSamplePlaybackGuide`)
- `OscType` (`definitions_cxx.hpp:358`): SINE, TRIANGLE, SQUARE, ANALOG_SQUARE, SAW, ANALOG_SAW_2, WAVETABLE, SAMPLE, DX7, INPUT_L/R/STEREO.

**Per-engine notes:**
- **Subtractive:** `Voice::render` calls `renderBasicSource()` for each source. Oscillators come from `dsp/oscillators`, wavetable rendering from `WaveTable::render` (`storage/wave_table/wave_table.cpp:1053`), samples from `VoiceSample`. Then filter set, then amplitude envelope.
- **FM:** 2 sources plus 2 modulators with feedback (`renderSineWaveWithFeedback`, `renderFMWithFeedback[Add]`, `voice.cpp` ~1440-1500).
- **Ringmod:** source 0 multiplied by source 1 (`voice.cpp` ~1299-1322). Only oscillator types up to WAVETABLE can be ring-modded (`kLastRingmoddableOscType`).
- **DX7:** an oscillator *type*, not a synth mode. It uses `unisonParts[u].sources[s].dxVoice` and `dsp/dx/*`. It is spread across `gui/menu_item/dx/*` (1.4k), `gui/ui/browser/dx_browser.cpp`, `storage/DX7Cartridge.cpp` and `gui/ui/keyboard/column_controls/dx.cpp`.
- **Wavetable:** `storage/wave_table/*` (1.5k): `WaveTable : AudioFile`, band data and reader. Loaded through `AudioFileManager`, referenced by `MultiWaveTableRange`.
- **Sample-based oscillator:** `Source` (`processing/source.cpp`) holds a `MultiRangeArray` of `MultisampleRange` (`storage/multi_range/*`). Each range has a `SampleHolderForVoice`. Playback uses `VoiceSample : SampleLowLevelReader` (`model/voice/voice_sample.cpp`, 1,790 lines), with optional `TimeStretcher` and `SampleCache` (cached repitched/rendered audio, `model/sample/sample_cache.cpp`, `sample_perc_cache_zone`).

**Per-sound render pipeline** (`Sound::render`, `sound.cpp:2383`, roughly lines 2480-2640):
1. arp post-processing (`process_postarp_notes`)
2. delay state setup
3. voice renders into a mono or stereo scratch buffer
4. pan
5. `processSRRAndBitcrushing`
6. `processFX` (ModFX + delay)
7. `processStutter`
8. `processReverbSendAndVolume` (adds to the global reverb buffer)
9. per-sound compressor

**Practical notes for slimming down:**
- **Lowest-effort wins by size:** the GUI makes up 38% of the code, so most of the reduction has to come from there. The cheapest GUI cuts are whole optional UIs — PerformanceView (2.1k), AutomationView (3.3k + 1.5k), keyboard layouts and chords (5.3k), the DX/arp/randomizer menus — plus MIDI Follow (2k) and stem export (1.3k).
- **Lookup tables:** `util/lookuptables` (9.5k) is data, not logic. It shrinks only if oscillator types are dropped.
- **USB:** removing USB host would cut part of `RZA1/usb` (34k), but MIDI over USB and the sysex/file features depend on it.
- **Easiest boundaries to cut along:** each `OutputType` / `OscType` / `ModFXType` / `SynthMode` / `ClipType` enum value. Code dispatches on these with `switch` / `if`, so removing a feature mostly means deleting enum cases and following compiler errors. The GLOB build helps.
- **Points every removal touches:** `currentSong`, `playbackHandler`, `AudioEngine::`, `display`, `soundEditor`, `view`, `getCurrentUI()`, `FlashStorage::`, `actionLogger`, and the `readFromFile` / `writeToFile` paths. Removing a feature that is saved in songs or presets also needs a decision about how old files load, since unknown XML tags are generally skipped.
